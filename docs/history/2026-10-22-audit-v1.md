# Audit du Compagnon Local face à Bionic Desktop

22 octobre 2026 — trois agents spécialisés, vérification de l’installation active et essais avec le modèle local déjà chargé.

Le Compagnon Local **1.10.0 possède déjà une boucle d’agent capable d’utiliser des fichiers, Internet et des scripts sur le PC**. Les essais réels le confirment avec Gemma. Il utilise les modèles servis par Bionic, mais **n’exécute pas automatiquement l’agent de Bionic Desktop et n’hérite pas de ses MCP, skills, sous-agents ou permissions**.

Pour ComfyUI, l’accès HTTP local depuis un script du compagnon est confirmé. Il reste à créer un outil de workflow et la restitution de l’image. Il n’est pas nécessaire de reconstruire la boucle générale d’appels d’outils.

## Neuf prompts exécutés avec le vrai modèle

Le code de production du compagnon a été importé depuis l’installation active. Le test a créé une instance limitée à `127.0.0.1` sur un port éphémère, avec un registre de projet et un magasin de conversations synthétiques sous `work/`. Aucun historique natif ni fichier personnel n’a été fourni au modèle.

Les requêtes ont suivi les vraies routes HTTP de connexion, de chat et d’approbation. Les appels au modèle, au web, aux interpréteurs et à ComfyUI étaient réels. Les neuf fichiers de production comparés étaient identiques au checkout audité. Cette méthode vérifie le backend utilisé par l’interface réseau ; elle ne constitue pas un nouvel essai sur téléphone ni un contrôle visuel du navigateur.

Les prompts ont utilisé le modèle Gemma déjà chargé, avec raisonnement désactivé pour ces essais courts et conversations indépendantes. Aucun chargement/déchargement de modèle n’a été demandé. Le test a produit **21 requêtes d’inférence**, **12 actions d’outil**, dont **11 réussites** et **un refus attendu**, et quatre validations de scripts prédéfinis.

P9 mesure uniquement la fidélité de la déclaration du modèle au schéma transmis, pas l’exécution des outils. P8 est un succès du test négatif, avec une action effectivement refusée. Une génération de conversation « completed » signifie que le tour est terminé, pas que toute action a réussi.

Pour les quatre scripts, le banc d’audit a accepté uniquement le code exact, le runtime, le dossier et le délai définis avant l’inférence ; tout autre code aurait été refusé. Les décisions ont traversé la route d’approbation de production. Ce n’était pas un clic humain sur téléphone et ce mécanisme de validation du banc n’a pas été installé dans le compagnon principal.

L’essai Python P5 utilise un interpréteur absolu connu dans la configuration de l’instance isolée. Un contrôle supplémentaire du même module de production, avec son réglage par défaut `python`, a également lancé **Python 3.12.10**, exitCode 0. Il n’a pas impliqué une nouvelle inférence.

La recherche web a fonctionné pendant cet essai. Cela ne garantit pas une disponibilité constante de DuckDuckGo ; son blocage intermittent reste possible et les tests simulés ne peuvent pas l’écarter.

## API Bionic : correction et nuance MCP

Il faut distinguer trois couches :

1. Le compagnon utilise **`/v1/chat/completions`**, en fournissant ses propres fonctions et en exécutant lui-même les `tool_calls`.
2. Bionic expose aussi **`/api/v1/chat`**, avec un contrat `integrations` pour des MCP configurés ou distants éphémères. L’existence de cette route a été confirmée par un POST vide retournant l’erreur HTTP 400 « model manquant ».
3. L’agent **Desktop** ajoute ses propres instructions, outils de shell, skills, contexte de projet et permissions. Aucun contrat vérifié ne permet d’affirmer qu’un simple appel HTTP récupère automatiquement cet agent complet.

L’ancienne formulation « l’API Bionic expose seulement l’inférence » était trop générale. Elle reste pertinente pour expliquer pourquoi le compagnon n’hérite pas de l’agent Desktop, mais **l’API native inclut aussi une voie d’intégration MCP**. La documentation décrit `integrations`, `allowed_tools` et `store:false`. [Contrat officiel](https://lmstudio.ai/docs/developer/rest/chat)

Un test supplémentaire a proposé à cette API un unique MCP éphémère d’audit sur une adresse `127.0.0.1`, avec un outil inerte `audit_ping` qui devait seulement renvoyer un marqueur. Aucun MCP personnel n’a été invoqué, aucun fichier de configuration modifié et `store:false` était demandé.

**Résultat réel : HTTP 400 avant toute inférence ou connexion au MCP.** L’erreur indique que les connexions MCP distantes dynamiques n’acceptent que des adresses publiques. Le serveur d’audit n’a reçu aucune requête et l’outil n’a pas été appelé.

Cette restriction signifie qu’un MCP ComfyUI local ne pourra pas être ajouté à cette voie par un simple `ephemeral_mcp.server_url=http://127.0.0.1:...`. Une intégration préconfigurée et autorisée est une autre voie documentée, mais elle n’a pas été testée ici. Il ne faut ni conclure à l’impossibilité de tout MCP local, ni promettre un accès automatique aux MCP du Desktop. Les ressources nomment `ng-mcp.json` et `mcp.json` pour des surfaces différentes ; leur équivalence n’est pas établie.

## Limites qui expliquent les écarts visibles

| Limite actuelle du compagnon | Conséquence pratique |
| --- | --- |
| **2 048 tokens de sortie maximum par appel au modèle** | Peut couper un script ou une réponse longue. Le plafond vient de `server.mjs`, indépendamment de la valeur choisie dans Desktop |
| Dix phases de modèle au plus, 24 actions cumulées | Une tâche complexe ne peut pas poursuivre indéfiniment sa boucle d’outils |
| Historique transmis au plus 36 messages et 24 000 unités de contenu, selon le budget | Le contexte chargé de 262 144 ne signifie pas que tout l’historique est transmis au modèle |
| Résultats d’outils non rejoués automatiquement au message suivant | Un « continue » n’a pas nécessairement les mêmes preuves de fichiers ou sorties d’outils que le tour précédent |
| Lecture directe : six fichiers distincts, 3 000 caractères/extrait, budget total au plus 12 000 caractères | Analyse ciblée possible ; une lecture exhaustive d’une grande bibliothèque demande une autre stratégie |
| Web : huit appels et 18 000 caractères sérialisés par tour ; pas de JS, cookies, connexion de compte ou LAN | Recherche et lecture passive, sans navigateur interactif ni accès aux API locales |
| Scripts : quatre propositions par tour ; 30 secondes par défaut, **120 secondes maximum** | Un workflow ComfyUI long devrait être soumis puis suivi par appels séparés ou par un outil de tâche asynchrone |
| stdout/stderr capturés jusqu’à 24 000 octets ; renvoi au modèle jusqu’à 4 000/2 000 caractères | Une sortie de commande volumineuse peut être tronquée |
| Sans projet : fichiers et scripts désactivés côté serveur | Activer ces outils demande un vrai projet de travail sélectionné |
| Script approuvé = droits du compte Windows, dossier initial du projet uniquement | Ce dossier n’est pas une sandbox. Un script peut lire ailleurs, appeler le réseau et lancer des programmes ; les réglages des outils fichiers/web ne limitent pas ce code approuvé |

Les outils fichiers directs contrôlent les chemins et les versions ; les scripts suivent un mécanisme d’approbation distinct. Ces capacités ne doivent donc pas être résumées à « accès complet activé/désactivé ».

## Ce que cela change pour une intégration ComfyUI

Les prérequis généraux sont déjà présents : le modèle sait demander un outil, le compagnon sait l’exécuter sur le PC et retransmettre le résultat, et l’accès à ComfyUI depuis ce processus est confirmé.

Pour une utilisation régulière depuis le téléphone, l’extension la plus directe serait :

1. Un outil dédié, par exemple `generer_image`, qui choisit parmi des workflows approuvés au format API et ne remplace que les paramètres prévus.
2. Un retour rapide avec l’identifiant de génération, puis un suivi d’état indépendant des délais de script.
3. La récupération de la sortie réelle et son rattachement au message du compagnon, avec aperçu d’image et téléchargement.
4. Des erreurs et reçus clairs : soumis, en cours, terminé, échoué ; aucune annonce d’image générée sur le seul succès de la soumission.

Le lecteur web public n’a pas besoin de recevoir un accès général au LAN pour cela. Un script approuvé suffit déjà pour un essai de passerelle ; un outil explicite sera plus pratique et plus contrôlable au quotidien.

**Aucun workflow n’a été soumis et aucune image n’a été générée pendant l’audit.** Le GET réussi ne valide ni un checkpoint, ni les nœuds, ni la mémoire disponible pour un rendu. Le chat peut afficher des images jointes, mais ses réponses Markdown et stdout ne créent pas automatiquement une pièce jointe à partir d’une image produite par ComfyUI.

## Tests automatisés complémentaires

Deux agents ont lancé des lots ciblés existants et partiellement communs :

- Lot outils/approbations/scripts/web/fichiers : **77 tests réussis sur 77**, hors environnement protégé restrictif.
- Lot élargi aux reçus et audits fichiers : **89 tests, 88 réussis, aucun échec, un test de lien Windows ignoré**, avec TEMP/TMP dans `work/`.

Ces totaux ne s’additionnent pas : de nombreux tests sont communs. Les premiers `EPERM` observés dans le TEMP système n’ont pas été reproduits après adaptation de l’environnement ou relance hors sandbox.

Les tests automatisés injectent les réponses du modèle et les transports web. Ils prouvent la logique des outils et permissions ; **les neuf prompts réels apportent la preuve distincte de leur utilisation par Gemma sur ce PC**. Les tests n’ont pas été ajoutés au produit et les sources sont restées inchangées.

## Ce qui reste non vérifié

- Parité d’exécution avec les mêmes prompts lancés dans une session Bionic Desktop : aucune nouvelle conversation native n’a été créée.
- Fonctionnement des MCP personnels et leur disponibilité éventuelle depuis l’API native.
- Navigation interactive Bionic : fonction désactivée, pas activée par cet audit.
- Exécution d’un workflow ComfyUI, image obtenue et affichage depuis un téléphone réel.
- Robustesse de tous les modèles, des sessions longues et des services web à d’autres moments.

Ces limites concernent la portée de la preuve ; elles ne retirent rien aux exécutions fichiers/web/PowerShell/CMD/Python/Node/HTTP local constatées.
